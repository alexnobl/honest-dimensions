
# HONEST DIMENSIONS
# Database Architecture and Design

**Database:** PostgreSQL
**Vector Extension:** pgvector
**Primary Key Strategy:** UUID
**Design Status:** Initial

---

## 1. Overview

The application uses PostgreSQL as its primary relational database.

The pgvector extension provides vector storage and similarity search for the RAG pipeline.

The database supports multi-tenancy, document versioning, conversations, AI workflows and security auditing.

## 2. Database Entities

### Identity and Organization

- users
- organizations
- memberships
- workspaces

### Document Management

- documents
- document_versions
- document_chunks

### Conversations

- conversations
- messages

### AI Workflows

- agent_executions
- approval_requests

### AI Configuration and Monitoring

- provider_configurations
- usage_records
- audit_logs

## 3. Relationships

- One user can have multiple organization memberships.
- One organization can contain multiple users.
- One organization can own multiple workspaces.
- One workspace can contain multiple documents.
- One document can have multiple versions.
- One document version can produce multiple chunks.
- One conversation can contain multiple messages.
- One user can initiate multiple conversations.
- One agent execution can generate multiple approval requests.

## 4. Multi-Tenancy

The system uses a shared-database, shared-schema multi-tenant architecture.

Relevant records contain organization ownership information.

Tenant isolation is enforced through:

- Authenticated organization membership.
- Backend authorization.
- Organization-scoped queries.
- Composite foreign keys.
- PostgreSQL Row-Level Security where appropriate.
- Tenant-filtered vector retrieval.

Organization identifiers supplied by clients must never be trusted without authorization.

## 5. Primary Key Strategy

UUIDs are used for primary keys.

This supports independent identifier generation and future distributed processing.

UUIDs do not replace authorization or access-control checks.

## 6. Document Versioning

Documents and document versions are stored separately.

The documents table represents the logical document.

The document_versions table represents individual revisions.

The document_chunks table stores extracted text and embeddings belonging to a particular document version.

A previous version must not be silently overwritten.

## 7. Vector Storage

Document chunks contain embeddings generated by a configured embedding model.

The embedding dimension must match the selected model.

pgvector will provide similarity search.

An HNSW index using cosine distance will be evaluated for efficient retrieval.

## 8. Indexing Strategy

Initial indexes:

- users.email
- memberships.user_id and memberships.organization_id
- workspaces.organization_id
- documents.organization_id and documents.workspace_id
- document_versions.document_id and version_number
- document_chunks.document_version_id
- conversations.organization_id and user_id
- messages.conversation_id and created_at
- agent_executions.organization_id and status

Vector indexes will be evaluated separately.

## 9. Data Integrity

The database will use:

- Primary keys.
- Foreign keys.
- Unique constraints.
- Not-null constraints.
- Check constraints.
- Composite tenant-aware foreign keys.

Important business rules will be enforced at the database level wherever appropriate.

## 10. Security Considerations

- Passwords must be stored using secure password hashing.
- Provider credentials must not be stored as plaintext.
- Sensitive data access must be authorized.
- Database access must use restricted application roles.
- Row-Level Security must be configured carefully.
- Tenant context must be safely managed with connection pooling.
- Audit records must capture relevant security events.

## 11. Future Improvements

Potential improvements include:

- Advanced vector indexing.
- Hybrid search optimization.
- Partitioning for large tables.
- Database read replicas.
- Archival strategies.
- Dedicated analytics storage.

These will be introduced based on actual requirements and measurements.

## 12. Design Status

This is the initial conceptual database design.

Detailed SQLAlchemy models, constraints, migrations, indexes and RLS policies will be implemented and tested during backend development.
